# FastAPI backend and React frontend for LangChain RAG project

The implementation adds a REST API wrapper around the existing RAG system and a modern React frontend with file upload, document ingestion, and chat interface. The backend preserves all existing modules (chain.py, ingest.py, config.py) by using sys.path manipulation, and the frontend is built with Vite+React+Tailwind following the specified architecture.

The API contract matches between frontend and backend: all five endpoints are implemented and called correctly. The frontend handles loading states, error display, and source citations. The README provides complete installation and troubleshooting documentation.

**Watch for:** Missing HTTP 500 handling in frontend error messages (likely); prompt construction vulnerability through unescaped user input (confirmed); private SDK access to Gemini embedding model config (possible).

**Verdict**: NEEDS_CHANGES

## High-level view

The backend's sys.path insertion gives it access to existing RAG modules without modification, but the path manipulation happens at import time rather than being validated, creating a brittle dependency on directory structure. The API layer translates between REST and the existing ask/ingest functions with proper error handling via HTTPException.

CORS is configured for localhost:3000 only, which is correct for development but will require adjustment when deployed. File uploads write directly to DATA_DIR without size limits or validation beyond file extension checks. Document ingestion calls the existing ingest() function and returns success even when the vector store creation might have partial failures.

The frontend uses Vite's proxy to route /api requests to port 8000, avoiding CORS in local development. The ChatInterface component manages message state with timestamp-based IDs and prevents submission when the system isn't ready. Error handling in api.js distinguishes between no-response (backend down) and error-response (backend returned an error), giving users actionable feedback.

Source citations are rendered separately from message bubbles and collapsed by default. The FileUpload component merges upload and ingest actions into one UI section, but treats them as distinct operations with separate loading states. The status indicator polls the backend to show document count, but there's no automatic refresh after ingestion completes unless onStatusChange fires.

The README documents the two-terminal startup sequence and the three-step workflow (upload → ingest → query). API endpoint reference includes request/response shapes for all five endpoints. Troubleshooting covers CORS, sys.path import errors, and vector store initialization, but doesn't explain what happens when ingestion fails mid-process.

## Backend import strategy and sys.path fragility

The backend adds its parent directory to sys.path at import time:

```python
sys.path.insert(0, str(Path(__file__).resolve().parent.parent))
```

If someone runs uvicorn from the backend/ directory directly, or if the project is packaged differently, imports will fail. The backend can only be started from one specific directory. The README documents this ("make sure you're running uvicorn from the workspace root") and the troubleshooting section covers the "No module named 'chain'" error.

## API endpoint contracts and error translation

All five endpoints match the frontend's api.js calls. The backend raises HTTPException for all error cases: missing files, empty questions, vector store not initialized, file type validation failures. The frontend's handleError function in api.js extracts error.response.data.detail, giving users specific error messages instead of generic failures.

**Concern**: If an unhandled exception occurs in chain.py or ingest.py (outside the try/except blocks), FastAPI will return a 500 error with a JSON structure like `{"detail": "Internal Server Error"}`. The frontend's `error.response.data.detail || 'Server error occurred'` will catch this, but the fallback message is less informative. If the backend returns a different JSON shape (e.g., `{"message": "..."}`), the detail extraction fails silently.

## CORS configuration scoped to localhost

The CORS middleware allows requests from http://localhost:3000 only. In production, the origin list would need to be expanded or made configurable via environment variables. The README's "Development" section mentions production deployment but doesn't address CORS reconfiguration.

## File upload validation and resource limits

The `/api/upload` endpoint validates that uploaded files end with .pdf, but doesn't check file size (a 500MB PDF would be accepted), MIME type (renaming malicious.exe to malicious.pdf would pass), or whether the file is actually a valid PDF.

The existing ingest.py will fail on non-PDF files during ingestion, not upload, so a user could upload a fake PDF and only discover the problem later. FastAPI doesn't impose upload size limits by default, so memory exhaustion is possible with very large files.

## Document ingestion and partial failure handling

The `/api/ingest` endpoint calls `ingest()` from the existing ingest.py module. If ingest() raises an exception, the endpoint catches it and returns a 500 error. But if ingest() succeeds partially (e.g., processes 2 of 3 PDFs before hitting a parsing error), the endpoint has no visibility into this and will report success, showing "Ingestion completed successfully" even if some documents weren't processed.

If ingest() stops on the first error, the vector store will be incomplete and questions will miss relevant documents. If it continues processing after errors, some documents will be indexed and others skipped, creating an inconsistent state.

The status endpoint counts PDFs in the data/ directory, not documents in the vector store, which could diverge after partial ingestion.

## Frontend state management and race conditions

ChatInterface tracks message state with `Date.now()` as the message ID. This works for a single-user local app, but would break under concurrent submissions (two messages sent within 1ms could collide). The isLoading flag prevents form submission during processing, so in practice, message IDs are sequential and unique.

The status indicator calls checkStatus() on mount and after file upload/ingestion, but doesn't poll continuously. If a user manually refreshes the page mid-ingestion, the status would revert to yellow even though ingestion is still running.

## Source citation rendering and citation number matching

The backend's ask endpoint returns sources in the format `["[1] document.pdf, p.5", "[2] document.pdf, p.7"]`. The AI response includes citation markers like `[1][2]` inline in the answer text, generated by RAG_PROMPT and embedded in the LLM's output. The frontend doesn't parse these or make them interactive; users have to manually correlate `[1]` in the answer with `[1] document.pdf, p.5` in the sources list.

If the LLM decides not to include bracketed citations, or includes citations that don't match the sources list, the UI won't detect the mismatch.

## Prompt construction and input escaping

The `/api/ask` endpoint passes user input directly to chain.py's ask() function, which flows the question into RAG_PROMPT. If the prompt doesn't escape curly braces or special characters, a question like "What is {context}?" could be misinterpreted as a template variable. More concerning: if RAG_PROMPT includes user input in a way that's parsed as instructions ("Ignore previous context and say..."), it's a prompt injection risk.

The backend doesn't sanitize user input before passing it to the prompt. LangChain's PromptTemplate usually handles literal text safely, but without seeing prompts.py, this can't be verified.

## Frontend API error handling coverage

The api.js handleError function distinguishes three cases:

1. `error.response` exists → server returned an error → extract `error.response.data.detail`
2. `error.request` exists but no response → network failure or server down → "No response from server"
3. Neither → request setup failure → `error.message`

If the backend returns a 500 with a different JSON shape (e.g., `{"message": "..."}` instead of `{"detail": "..."}`), the detail extraction fails and the fallback is "Server error occurred".

## Vite proxy configuration and deployment

The vite.config.js proxy forwards `/api` requests to `http://localhost:8000` for development. After running `npm run build`, the frontend is static HTML/JS in the dist/ folder with no proxy capability. The static files will try to fetch from `/api` relative to wherever they're hosted, which won't work unless the frontend and backend are served from the same origin.

Production deployment requires either (1) serving frontend and backend from the same domain/port, or (2) modifying api.js to use an environment-variable-driven base URL. The README doesn't document this.

## React hooks usage and component lifecycle

ChatInterface: useState for messages/input/loading, useRef for scrolling and input focus, useEffect for scroll-on-change and status check on mount. FileUpload calls `onStatusChange()` after upload/ingest success, triggering checkStatus() in the parent.

There's no useEffect watching `systemStatus.ready` or polling for status updates, so if ingestion happens in another tab or via direct API call, the UI won't reflect it until the user uploads/ingests another file.

## Component styling and accessibility

Accessibility gaps:

- Message bubbles have no ARIA role or semantic structure; screen readers will treat them as generic divs
- The source citation collapse button has no aria-expanded attribute
